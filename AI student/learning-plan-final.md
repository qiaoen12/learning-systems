## 1. 学习者定位

- 转行，无语言基础。
- 能提需求、组织上下文、验收结果、做产品判断。
- 过去很多系统由 AI/Codex 在你的方向性指导下完成，本人尚不能稳定独立读、写、调代码。
- 最大风险不是学得慢，而是继续停留在“AI 写得出来，但我解释不了、修不了、验收不了”。

16 周后的目标不是成为算法研究员，而是成为：

> 能看懂、能搭建、能调试、能验收 AI 应用系统的创业型学习者。

---

## 2. 核心原则

### 原则 1：最小系统原则

所有学习只围绕一个问题：

> 我能不能自己写出一个能跑、能解释、能验证的小系统？

不做：

- OS 理论深挖
- Transformer 数学推导
- Kubernetes / Terraform / 微服务治理
- fine-tuning
- 多框架横跳

做：

- 能运行
- 能调试
- 能保存数据
- 能调用模型
- 能检索和引用
- 能评估质量
- 能解释成本和风险

### 原则 2：单链路原则

每阶段只有一个主链路，不并行开多个系统。

| 阶段 | 主链路 |
| --- | --- |
| Week 1-4 | CLI -> HTTP -> FastAPI -> SQLite |
| Week 5-8 | 数据查询 -> Debug -> 系统认知 -> LLM API |
| Week 9-12 | Embedding -> RAG -> RAG 评估 -> Agent |
| Week 13-16 | Workflow -> 产品判断 -> 学习性整合 -> 部署闭环 |

### 原则 3：产品驱动原则

每周必须回答：

> 这个能力对应真实 AI 产品里的哪一个功能或风险？

但产品驱动不等于立刻做商业项目。前 16 周的项目都是学习性练习，用来训练能力，不作为正式创业项目启动。

- 准备一个 `questions.md` 保存不懂的问题。
- 确认 Python、虚拟环境、编辑器、终端能正常使用。

- 能运行 `python --version`。

前 16 周固定：

- 语言：Python

## 6. 每周统一 Definition of Done

每周除了本周 Exit Criteria，还必须满足这 5 条：

- 代码或练习能跑通。
- 你能脱离 AI，用自己的话解释本周主链路怎么流动。
- 至少保留 1 个失败样本和修复过程。
- 有可存档产物：代码、日志、图、测试表、周报至少一种。
- 没有触发“反退化阀门”。

不满足 DoD，不进入下一周。

## 7. 旧系统对照规则

已有系统只做可选映射，不做硬前提。

执行顺序固定为：

1. 先完成本周全新、最小、自建练习。
2. 再写清楚本周概念。
3. 如果还有余力，再把概念映射到旧系统。

禁止把“旧系统太复杂、我还没看懂”当成拖延本周练习的理由。

### Phase 2：数据系统 + Debug 能力（Week 5-8）

#### Week 5：SQLite 强化 + 索引

**为什么这一周存在**

**目标**

**学习**

- SQLite Query Planning / Index 基础。
- DDIA 第 3 章：存储与检索，重点 B+ Tree。

**练习**

- [ ] 构造 10 万行数据。
- [ ] 写一个慢查询，记录无索引耗时。
- [ ] 加索引，记录加索引后耗时。
- [ ] 写下为什么索引能加速。
- [ ] 手画 B+ Tree 简化结构。

**可选映射**

**Exit Criteria**

- 能用 B+ Tree 解释索引为什么快。

#### Week 7：系统结构认知

**为什么这一周存在**

**目标**

**学习**

- DDIA 第 5 章：Replication。

- DDIA 第 7 章：Transactions。

**练习**

- [ ] 给 API 加一个简单缓存层：可用内存 dict 或 SQLite 表，不强制 Redis。
- [ ] 写一个简单限流器：每个用户每分钟最多 N 次。
- [ ] 画系统图：用户 -> API -> 缓存/限流 -> DB。
- [ ] 写一页说明：复制、分区、事务分别解决什么问题。

**可选映射**

**Exit Criteria**

- 能解释复制、分区、事务的基本概念。

### Phase 3：RAG 系统（Week 9-12）

#### Week 14：产品判断（创业分水岭 2）

**为什么这一周存在**  
防止把一个技术练习误认为值得投入的产品。

**目标**  
回答：为什么有人用这个，而不是直接用 ChatGPT？

**学习**

- 用户问题定义。
- 任务频率、痛点强度、付费意愿。
- 成本、延迟、质量三角。
- 数据闭环。

**练习**

- [ ] 选 3 个你感兴趣的 AI 场景，各写一页判断：
  - 用户是谁？
  - 高频问题是什么？
  - 现有替代方案是什么？
  - AI 带来的增量是什么？
  - 如何验收质量？
  - 成本是否可控？
  - 数据如何沉淀并改善系统？
- [ ] 给每个场景打分，选出一个后续最值得做 MVP 的方向。

**Exit Criteria**

- 能区分“技术上能做”和“商业上值得做”。
- 能说明 AI 产品如何从用户反馈中变好。
- 能解释为什么复杂 Agent 会增加成本和延迟。
- 能选出一个后续 MVP 方向，但不要求本周启动项目。

#### Week 15：学习性 MVP 整合

**为什么这一周存在**  
你要第一次把前 14 周能力连成一条端到端链路，但这仍是学习样机，不是正式商业项目。

**目标**  
整合 RAG、Agent、API 和日志，形成可解释样机。

**练习**

- [ ] 整合一个学习性 MVP：
  - 知识库 RAG
  - 对话历史
  - 工具调用
  - FastAPI API 层
  - CLI 或最简 Web 页面
- [ ] 记录单次会话 token 消耗。
- [ ] 记录一次完整链路日志：输入、检索、工具、回答、成本。

**Exit Criteria**

- 样机能回答知识库内问题。
- 能调用至少 2 个工具。
- 有对话历史。

## 10. 反退化阀门

出现任一情况，本周自动暂停推进，只做补课和复盘：

- 连续 3 天只是复制报错给 AI，自己无法解释。
- 本周主要代码 70% 以上来自 AI，且你讲不清输入、处理、输出。
- 功能能跑，但你完全解释不了主链路。
- 一个概念反复听懂但做不出来。
- 同时追 3 种以上框架或工具。
- 报错只会贴给 AI，不知道文件、行号、输入、输出。

暂停后只做四件事：

1. 回到最近一个能跑通的练习。
2. 把问题缩小到 20 行以内代码。
3. 写下“我以为会发生什么，实际发生了什么”。
4. 只问 AI 解释概念或定位思路，不直接要完整代码。

## 12. 16 周后路线

验收通过后再二选一。

### 路线 A：AI 创业 MVP

- 选一个真实场景做 4 周 MVP。
- 建评估集。

- 学系统设计基础。
