## 它解决什么问题

这个仓库把检索增强生成的各种技术整理成带说明和可运行 Notebook 的条目：切片策略、查询改写、假设性问题、上下文压缩、重排序、融合检索、层级索引、自省式检索等。每种技术都写清了它针对什么失败模式。

它解决的是 RAG 学习中最典型的卡点：教程版的 RAG 十分钟就能跑通，但一换成真实文档，答案就开始不准，而你不知道该动切片、动检索、动 prompt 还是补文档。这个仓库是从症状反查手段的索引。

## 何时开始

**必须先自己手写过一遍最小 RAG**：读文档、切片、生成 embedding、算相似度、拼 prompt、调模型。在这之前打开它，只会变成收集一堆没有上下文的技巧名词。

先手写的原因是：这些技术全都是对基础链路某一步的改进。没有基础链路作参照物，你无法判断某项技术在改什么，也无法验证改完是否更好。

## 建议的学习方式

按症状查，不按目录读。

| 你观察到的症状 | 查哪一类 |
| --- | --- |
| 检索出的片段主题对但没有答案 | 切片策略、层级索引 |
| 用户问法一变就检索不到 | 查询改写、假设性问题 |
| 检索回来一堆相关片段，但答案被淹没 | 重排序、上下文压缩 |
| 答案里混入了别的文档的内容 | 融合检索、元数据过滤 |

选中一项后，**一次只改一处**，并用固定的测试问题集对比改前改后。同时改两处，你就不知道是哪一处起了作用——这也是为什么它必须和 [LLM 评测](./03-llm-evals.md) 配合使用。

## 最小验收

- 能说出自己 RAG 的一个具体失败模式，而不只是“回答得不太好”。
- 针对该失败模式选一项技术，实现后用测试集给出改前改后的对比数字。
- 能解释这项技术为什么对这个失败模式有效，以及它带来的代价（延迟、成本或复杂度）。

## 并行与下一步

与 [LLM 评测](./03-llm-evals.md) 强绑定使用：没有评测就无法判断某项技术是否真的改善了效果，只能凭感觉。

同作者的 `NirDiamant/GenAI_Agents` 是 Agent 侧的对应仓库，等进到 Agent 阶段再看。

## 现在不做什么

不要把技术列表当成清单逐项实现。绝大多数真实 RAG 只需要其中两三项，用哪几项取决于你的文档结构和用户问法，不取决于列表长度。
