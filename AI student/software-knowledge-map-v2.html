1. 对上一版的反思

核心审计结论：上一版没有认真逐章分析所有原版书籍内容。它完成了“资源定位”和“粗粒度骨架”，但没有把每本原书的目录结构、思想主线和证据强度写清楚。因此它不能被当成“已深读全部原书后的最终图谱”。

遗漏 1：证据等级缺失

上一版把 TYCS、roadmap.sh、细分资源混在同一叙述层，没有标明哪些来自原书公开目录，哪些只是官方介绍或二手定位。

已修正新增证据等级

遗漏 2：原书内容太粗

SICP、OSTEP、Crafting Interpreters、SRE、Twelve-Factor 等书或材料有清晰结构，上一版只提了概念，没有把结构映射进骨架。

已修正新增书本结构摘要

遗漏 3：工程层被写薄

Software Engineering at Google 的核心不是“代码评审”几个词，而是时间、变化、规模、成本。Twelve-Factor 也不是部署口号，而是一套服务运行纪律。

已修正覆盖层细化

遗漏 4：AI 应用边界不够硬

上一版说 AI 应用是专业延伸，但没有解释为什么。更准确地说，RAG / Agent 不是传统 CS 主干，却依赖数据、网络、后端、可靠性和评估体系。

已修正仍需独立资源验证

遗漏 5：安全的地位仍不稳

Security 在 TYCS 里不是一级主干，但在 roadmap.sh Backend 里很突出。它既不是普通工具，也不是单一学科入口，应暂放横向层并等待你决策。

保留争议不隐式裁决

遗漏 6：DDIA 版本判断不严谨

上一版已修正为不指定 2e。HTML 版继续保留这个谨慎处理：没有官方来源确认前，不把版本升级写成事实。

保留待核查不伪装确认

2. 证据等级

等级 含义 可以如何使用
A 核查到公开目录、开放文本或官方章节结构。 可以作为骨架判断的强证据，但仍不等于逐字读完全书。
B 核查到官方介绍、课程页面、书籍主页或稳定目录线索。 可以支持资源归位，但不应过度提炼细节。
C 主要来自 TYCS 推荐、roadmap.sh 对照或常识性学科定位。 只能作为候选位置，必须进入争议或待验证。
本次修正仍然不是“读完全部原版书籍”的结果。它是“基于可公开核查结构的骨架审计版”。如果要达到严格意义上的原书研究，需要逐本做目录、前言、章节摘要、核心概念、反例和适用边界的阅读卡片。

3. 修正后的全局骨架

4. TYCS 主干，按原书结构修正

这一节只保留主干骨架，不展开学习任务。每个节点增加“原书结构线索”和“上一版修正点”。

1. 编程思想与抽象：SICP / CS61A

证据等级：A。SICP 公开目录可核查到过程抽象、数据抽象、模块化/对象/状态、元语言抽象、寄存器机器。

修正：上一版只写“抽象、递归、解释器”，太薄。更准确的骨架是：过程抽象 -> 数据抽象 -> 状态与对象 -> 语言解释器 -> 机器模型。

过程数据状态解释器寄存器机器
2. 计算机体系结构：CSAPP / Nand2Tetris

证据等级：B。CSAPP 官方页确认其定位是程序员视角的计算机系统；Nand2Tetris 项目页确认其以 12 个项目从硬件到软件栈。

修正：上一版没有明确两者差别。CSAPP 是“真实机器如何运行程序”，Nand2Tetris 是“从 NAND 到可运行系统的纵切直觉”。二者不是同一个入口。

数据表示内存层级链接系统调用性能边界
3. 算法与数据结构：Skiena / Roughgarden / How to Solve It

证据等级：B。TYCS 明确偏向 Skiena，roadmap.sh 也强验证数据结构、渐进复杂度、搜索、排序、图、字符串、复杂度类。

修正：上一版正确反对刷题化，但缺少“算法目录的用途”。算法节点应服务于问题建模、成本估计、可行性判断，而不是把题型清单当知识地图。

复杂度图搜索动态规划难解问题
4. 计算机数学：离散数学 / 线性代数

证据等级：B。TYCS 将离散数学、逻辑、组合、概率、集合、图论、数论和线性代数列为 CS 数学底座。

修正：上一版把数学写成“理论主干”，但没有说明它不是单独为了考试，而是为算法正确性、复杂度、密码、ML、图结构提供表达语言。

证明组合概率图论线性空间
5. 操作系统：OSTEP

证据等级：A。OSTEP 公开页面明确分为 Virtualization、Concurrency、Persistence，并包含 CPU scheduling、memory API、threads、concurrency bugs、files、file systems、RAID、NFS 等章节。

修正：上一版写“进程、线程、内存、文件”还不够。OS 主干应按三件事组织：虚拟化资源、处理并发、保证持久化。

VirtualizationConcurrencyPersistenceI/OKernel boundary
6. 计算机网络：Top-Down / Wireshark

证据等级：B。TYCS 推荐 Kurose/Ross，强调 top-down 和 Wireshark labs。

修正：上一版把网络和 Web API 接得太快。网络主干应先是分层、端到端、可靠传输、拥塞、路由、DNS、HTTP/TLS，再落到 Web 后端。

分层端到端TCP/UDPDNSHTTP/TLS
7. 数据库：CS186 / Architecture of a Database System / Red Book

证据等级：B。TYCS 明确推荐 CS186、DBMS 架构论文、Red Book，并特别指出 data modeling 常被忽视。

修正：上一版把数据库写成“存取、索引、事务”还不够。更高视野是：查询处理、存储管理、索引、并发控制、恢复、优化器、数据建模共同构成 DBMS。

存储查询优化事务恢复数据建模
8. 编程语言与编译器：Crafting Interpreters / Dragon Book

证据等级：A。Crafting Interpreters 公开目录显示三段结构：语言地图、树遍历解释器、字节码虚拟机，并覆盖 scanning、parsing、functions、classes、closures、garbage collection、optimization。

修正：上一版说“语言如何表达、约束、翻译和执行”是对的，但应更明确：语言工具链从词法/语法，到 AST / 解释执行，再到字节码、VM、闭包、GC 和优化。

ParsingASTVMClosuresGC
9. 分布式系统：DDIA / MIT 6.824

证据等级：B。TYCS 推荐 DDIA、Distributed Systems 3e、MIT 6.824 和论文阅读；DDIA 官方页确认其聚焦数据密集型应用、可扩展性、CAP、最终一致性、分片等主题。

修正：上一版把分布式系统和后端规模化贴近了，但还要强调它的本体是失败模型、复制、分区、一致性、事务、共识、批处理和流处理。

复制分区一致性共识流处理

5. 现代工程覆盖层，重新细化

软件设计与工程实践

资源：A Philosophy of Software Design、Software Engineering at Google、Google Engineering Practices。

修正：不只是一组最佳实践。它解决的是代码在时间、变化、规模和成本下还能不能保持可理解、可修改、可评审。

复杂度模块边界测试评审

Web / API / 后端服务

资源：MDN HTTP、roadmap.sh Backend、REST、GraphQL、gRPC、OpenAPI。

修正：它不是 CS 主干，但它是网络、数据库、分布式系统在产品服务里的主要汇合点。

HTTPAPI contractAuthCaching

架构判断

资源：Martin Fowler Architecture Guide、AOSA。

修正：架构不是画大图。更准确地说，它关注共享理解、早期希望做对的决策、高代价变更，以及系统演化能力。

决策演化边界案例

云原生服务纪律

资源：Twelve-Factor App。

修正：应拆成 codebase、dependencies、config、backing services、build/release/run、processes、logs 等纪律，而不是只写“部署原则”。

ConfigLogsProcessesParity

可靠性与生产系统

资源：Google SRE Books。

修正：SRE 层不是运维杂项。它提供监控、自动化、发布工程、告警、应急响应、事故管理、复盘、可靠性测试和关键状态管理。

SLOMonitoringAlertingPostmortem

AI 应用与安全

资源：本轮没有做完整 AI / Security 原书级验证。

修正：RAG、Agent、Evals 先作为专业延伸；Security 先作为横向关注点。二者都重要，但不能在本图谱中偷换成 TYCS 一级主干。

7. 技术词定位，作为验收样例

技术词 定位 不应误判为
Python 语言实例，挂在 Programming 与 Languages 下。 计算机科学主干本身。
FastAPI 后端框架，挂在 Web / API / Backend 服务层。 架构能力或网络理论。
SQLite 数据库产品，用于理解 SQL、索引、事务、持久化。 数据库学科全部。
HTTP 网络应用层协议，同时是 Web / API 基础。 单纯后端框架知识。
Docker 交付与环境封装工具，挂在云原生服务纪律。 计算机主干。
RAG AI 应用模式，依赖文档处理、Embedding、检索、数据库、LLM API。 数据库或算法的替代品。
Agent AI 应用模式，依赖任务分解、工具调用、状态、评估、可靠性。 自动等同于架构能力。
