# Corpus-First 3.2：AI 分工、代码契约与阀门

方案版本：3.2
结构版本：clean-1
适用范围：`corpus-guard` 的全部开发过程

本文件的规则优先于代码的优雅、简洁、性能和通常所谓的「最佳实践」。唯一目的是让学习者真正能读懂并接管实现。

## 1. AI 分工规则

常见做法是让 AI 定规则、自己抄代码。本方案反过来：**判断力就是规则，规则一外包，能力就不会长。** 测试用例是唯一 AI 帮不了你、又能证明你真的理解了输入输出契约的产物。

但一次性切到最严会卡在起跑线上，所以分两段。

### 1.1 宽松期：2026-09-01 至 09-14

AI 可以给规则模板，但必须走完这个流程，缺一步作废：

1. AI 列出候选校验规则，可以一次给 20 条。
2. **逐条处理，每条只有三种结果：删掉、改写、保留。** 保留的必须写一句「它在防什么真实问题」。
3. 三种结果的条数记进 `corpus-guard/docs/DECISION_LOG.md`。
4. 删掉的条数如果是 0，说明你没在判断，这一轮作废重来。
5. 最终留下的规则里，**至少 4 条必须是 AI 没提、你自己从数据里看出来的**。

第 5 条是宽松期唯一的硬门槛，它保证你不是在抄，而是在补。

**提前转严的条件**：宽松期内出现一次「你删掉的 AI 规则超过一半」，说明判断力已经起来了，直接进严格期，不用等 09-15。

### 1.2 严格期：2026-09-15 起

| 产物 | 谁做 |
| --- | --- |
| 判据、校验规则、测试用例的**语义** | **只能自己**，先用中文写在纸上再碰键盘 |
| 测试代码的实现 | 可以 AI |
| 校验器的实现 | 可以 AI |
| 数据合约文档 | **只能自己**，AI 只能解释字段含义 |
| 失败样本的根因判断 | **只能自己** |

### 1.3 零基础可执行的代码审查法

一条中文规则必须对应一个 pytest 裸函数，函数名就是规则的英文缩写。审查分两步：

1. 数一数规则条数和测试函数个数是否相等；
2. 再逐对对读，一条规则对一个函数。

不用会写 Python 也能验证「代码是不是在做我说的事」。这是零基础阶段唯一可执行的审查方式。

## 2. 卡住时的升级阶梯

两段都适用，因为「不许问」是最容易让人停下来的规则。

| 卡住时间 | 允许做什么 |
| --- | --- |
| 0–20 分钟 | 自己读报错，看文件和行号，打印中间值 |
| 20–60 分钟 | 问 AI **思路和概念**，不要完整代码；把问题缩到 20 行以内 |
| 60–90 分钟 | 要 AI 的代码，但必须先写下「我原以为会发生什么，实际发生了什么」 |
| 超过 90 分钟 | **允许直接读采集器源码**（`merge_and_summarize.py` 等）。前提是先写下「我卡在哪一条规则上」，读完之后补一条 pytest 把这个理解固化下来 |

最后一行是故意的。L2 说「不看采集器代码」是为了让你先自己想，不是为了让你卡死一整天。读源码是正当手段，只要它发生在你已经有具体问题之后，而不是之前。

## 3. 代码风格契约（给 AI 的硬约束）

每次让 AI 写或改 `corpus-guard` 的代码，都要附上这一节。

### 3.1 禁止

- `class`。全部用普通函数。
- `unittest.TestCase`、`setUp`、`tearDown`。测试只用 pytest 裸函数加裸 `assert`。
- 类型注解，例如 `-> None`、`: dict[str, int]`。L2 之前一律不要。
- 列表推导式和字典推导式。用 `for` 循环加 `append`。
- 装饰器，包括 `@pytest.mark.parametrize`。要测多个频道就写多个函数，重复没关系。
- `importlib`、动态导入、元编程、`__future__`。
- 一行里超过两个点的链式调用。`Path(__file__).resolve().parents[1]` 要拆成三行。
- 内联嵌套字面量。嵌套的 `dict`/`list` 必须先赋值给有名字的变量，再传进函数。
- 三元表达式、`lambda`、walrus `:=`、`*args`、`**kwargs`。

### 3.2 要求

- 每个函数不超过 15 行，一个函数只做一件事。
- 变量名用完整英文单词：`message_count`，不用 `mc`、`cnt`、`n`。
- 一行只做一件事。中间结果宁可多存一个变量。
- 每个函数开头一句中文注释，只说「这个函数拿什么、还什么」，不解释怎么做。
- 报错要带上下文：哪个文件、哪个频道、哪条记录的哪个字段。
- 重复优先于抽象。现在能逐行读懂比减少行数重要。

### 3.3 验收方式

随机指一个函数，逐行说出：

- 这一行读了什么；
- 改了什么；
- 可能返回或报出什么。

**有一行讲不出，就让 AI 按契约重写那个函数——不是让 AI 解释它，是让 AI 重写它。** 这个区别很重要：读不懂的代码不是你的问题，是代码的问题。「AI 能解释」不等于「学习者已接管」。

写在这里的每一条都会让代码变长、变笨、变得不像专业 Python。这是刻意的。等你能读了，再谈优雅。

## 4. AI 断电测试（四级阶梯）

每层结束时执行一次，关掉所有 AI 工具，限时 30 分钟。

| 级 | 断电后要做到 | 对应层 |
| --- | --- | --- |
| 跑 | 让当前层代码从零跑起来（进目录、激活环境、执行命令），并说出输出里每个数字的含义 | L0.5 |
| 读 | 制造一个真实报错，读 Traceback，说出是哪个文件哪一行、哪一类错误（语法/路径/类型/数据） | L1 |
| 修 | 独立修掉一个 20 行以内的 bug，不问 AI | L2 |
| 写 | 从空文件写出一条新校验规则的完整实现 | L3 及以后 |

做不到，这一层不算过，但**不算失败**——回到上一级再练一次，再重测。

这个阶梯的意义在于「跑」这一级零基础第一周就能达到。旧方案那个不分级的版本对零基础的人在 L1 就是不可能任务，所以它从未被执行过。

## 5. 入口阀门：检测「没在学」

替代旧路线的反退化阀门。那套阀门检测「学得不对」，这套检测「根本没进门」。

**触发条件：`corpus-guard` 产生第一个 commit 之后，连续 7 天没有新 commit。**

触发后强制执行两件事：

1. 当前层的目标砍半，重新拆到「今晚能出一个 commit」的粒度。
2. **禁止新增「关于学习本身」的元文档**，直到 `corpus-guard` 出现一次新 commit。

第 2 条的范围必须精确，否则会误伤正常工作：

| | 内容 |
| --- | --- |
| **禁止** | 学习路线、课程清单、知识地图、技能树、资料索引、教程翻译工程、任何一份新的学习计划 |
| **不禁止** | 业务与行业研究、竞品与市场资料、语料分析结论、`corpus-guard` 自己的 `CORPUS_MAP.md` / 数据合约 / `DECISION_LOG.md` |

判断标准一句话：**它是在描述「我要怎么学」，还是在描述「我发现了什么」？** 前者禁，后者不禁。

这条不是通用建议，是针对已经发生过的具体失败模式：8 周里规划类文档的产出速度远高于代码，而这类文档带来的进步感是虚假的。旧方案写了「禁止因为资料焦虑扩展阅读清单」，但没有任何东西执行它——没有触发器的规则只是愿望。

## 6. 门内阀门：检测「学得不对」

旧路线的六条继续保留有效。出现任一情况，暂停推进：

- 连续 3 天只是把报错复制给 AI，自己无法解释。
- 主要代码 70% 以上来自 AI，而且讲不清输入、处理和输出。
- 功能能跑，但完全解释不了主链路。
- 一个概念反复觉得听懂，却仍做不出来。
- 同时追 3 种以上框架或工具。
- 面对报错仍不知道文件、行号、输入和输出。

暂停后只做四件事：

1. 回到最近一个能跑通的版本。
2. 把问题缩到 20 行以内。
3. 写下「我以为会发生什么，实际发生了什么」。
4. 按第 2 节逐级求助，不直接扩展功能。

入口阀门和门内阀门都不用于评价人，只用于及时改变练习粒度。
